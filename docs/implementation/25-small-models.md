# Plan 25: Planning with small models

* **Status:** Implemented. This text describes the system as built.
* **Needs first:** Plans 12, 17, 21, 23, and 24.
* **Implements:** FR-353 to FR-355 and PRD decision D70. It narrows PRD decision D61 and FR-310 for the criteria pipeline, and adds the TRD section "Planning one criterion at a time".

## Goal

`semar plan` works well with a strong model, and badly with a small one. The planner has one open-ended job: explore the repository with the read tools, find the routes, read the handlers, and write every scenario of the release. A small model such as Claude Haiku gets lost in it. The goal is a plan that a small, cheap model makes as well as a strong one: Claude Haiku and Sonnet, and the Codex model gpt-6-luna, and not only Opus.

The change is of the shape of the job, not of the model. Code does the research that the planner did with tools. A model answers a small closed question for one acceptance criterion. Code checks the answer. Only an answer that fails the checks goes to a bigger model.

## Decisions

| # | Decision | Reason |
| --- | --- | --- |
| D1 | `semar plan --pipeline criteria` plans one acceptance criterion at a time. Code reads the ticket files and builds a packet for each criterion. A job with no tools answers each packet in a closed schema. Code checks the answer, sends a failing answer back once to the same model with the problems in plain words, and then to the next model of the ladder. Code assembles the accepted answers into the same draft that the single planner returns, so the validation, the trial, the scenario files, the obligations, and plan.md are the same. `--pipeline single` is the other value and the default (D12) | Each of the things that a small model got wrong in one big job is now either found by a program or checked by one. What is left for the model is to choose, from lists, how to test one sentence |
| D2 | A packet holds: the cite and the text of the criterion; the operations of the API documents that the ticket reaches; the diff of the ticket's files, cut at `MaxPacketDiffBytes` (16 KiB), whole files first and ranked as the plan's own diff is; the fixtures with their parameters and outputs; the accounts with their descriptions and the default account; and the scenarios of the ticket that exist. An operation is reached when its route or operationId is in the diff of the ticket's files or in the text of the ticket, or when a changed source file registers its route (`POST "/v1/orders/{id}/refunds", h.Refund`, `router.post('/x', refund)`, or a decorator over a function) to a handler whose name is on a line of the diff that changed or in the function context of a hunk. A criterion that names a route puts that operation first. The operations that share a word of their path with a reached one follow, because a scenario that changes a record has to create it and read it again, and so does the rest of the document when the whole document has at most 24 operations. Each operation carries its method, its route with the prefix of the document, its summary, its path and query parameters, the properties of its JSON body with type, required, nullable, and enum, and the JSON paths of each response that the document describes. Only operations with a method that the environment allows are kept | The planner used to find these with `Grep` and `Read`, turn by turn. The same evidence in the prompt costs one pass, and a model that cannot see an operation cannot invent a use of it |
| D3 | A job has no tools, and its answer is its only output. Claude Code runs with `--tools ""`. Codex runs with its `shell_tool` and `unified_exec` features off. An API kind offers only the `submit` tool. The schema goes to a harness as `Job.SchemaInPrompt`: Codex gets it as text in the prompt and the output is checked afterwards, because Codex's strict structured output narrowed the choices of gpt-6-luna on this schema until it answered `notDrafted` to all 16 criteria of the measured release (see Measured), and the same schema in the prompt gave 15 and then 16 answers. Claude Code enforces it as the schema of its answer tool, which a small model handles. The turn limit is `CriterionMaxTurns` (2): one turn to answer, and one that a harness may use to return the answer. A job runs in an empty directory of its own, so no job can see the copy of the source. At most `MaxParallelJobs` (4) jobs run at once. The person's MCP servers and skills are never loaded, and `--with-setup` with `--pipeline criteria` is an error | A job with nothing to call cannot loop, wander, or read an instruction in the repository. The first turn of such a job costs about 5,000 input tokens, and not 57,000 |
| D4 | The answer is one object with one `answer`, and the answer is exactly one of `scenario`, `manualCheck`, and `notDrafted`, each with its own fields. A scenario has a title, an intent, `given` entries, and steps. A step has an `id`, `setup`, an account `as`, an `action`, an `operation`, `path` and `query` parameters, `body` fields, `captures`, and `expect` checks. The schema is made from the packet: `operation` is an enum of the packet's operation keys, `as` an enum of the accounts, `fixture` an enum of the fixtures with the parameters of each, a path or query parameter name an enum of the ones the operation declares, a body `field` an enum of the declared fields, and the `value` of a field is any scalar, with the type of the field, its enum, and its nullability said in words, or the JSON text of an object or an array. A capture's JSONPath is an enum of the fields of the success responses. A check is `{subject, name, operator, value}` with `subject` one of `status`, `jsonpath`, `header`, and `operator` one of `equals`, `notEquals`, `contains`, `exists`, `notExists`, `greater`, `less`, `count`, `equalsPath`. Every object lists all its properties as required and allows no other, which is the form that every harness accepts. The parts that every operation shares are defined once under `$defs` | JSON Schema can say which names are allowed, and a model that is made to choose from a list cannot write a name that is not on it. What it cannot say, such as "this field is required", is checked by code (D5) |
| D5 | The model never writes a method, a path, a hint, a host, a header, a credential, or the cite. Code takes the method, the hint, and the path from the operation, with each path parameter filled with the value that the answer gave. The cite of each expectation is the cite of the criterion and its first sentence, with `source: ticket`. A path parameter must be written as `{{name}}` of an earlier capture or a fixture output, or as `missing-{{run.id}}`; a literal ID is a problem unless the document lists it as an enum value | These are the parts that a small model invents. A wrong method or path cannot be written, and a cite cannot point at the wrong line |
| D6 | Code checks each answer, and each problem is a sentence in plain words that names the place and says what is right: `field amountt does not exist in post_v1_orders_orderId_refunds; its fields are amount, reason`, `field amount is required by post_v1_orders_orderId_refunds and is missing`, `path parameter orderId must be written as {{name}} of an earlier capture or a fixture output, or as missing-{{run.id}} for an ID that cannot exist; the literal "o_1" is an ID that no step or fixture gave`, `the check reads $.data.refundedTotl, which no response of getOrder declares; its response fields are $.data, $.data.id, ...`. The checks are the schema, the fields and parameters of the operation, the types and enums of the values and the required fields (not in a step that expects a status of 400 to 499, which tests a validation rule and may send a value of another type or leave a required field out, but still never a name that the document does not declare), the response fields of a check and a capture, a setup step with no result, a step with no result, and then the rules of the whole draft for the one answer, run as a draft of its own: titles, step IDs, variables that are used before a capture, the fixtures and their parameters, the accounts, the manual check and `notDrafted` rules. A check cannot compare with `null`, which a scenario cannot hold, and the problem says so | A correction that says exactly what is wrong succeeds far more often than a request to try again, and a small model can follow a sentence like that |
| D7 | A failing answer goes back once to the same model: the same packet, the answer that failed, and every problem. If the correction fails, the criterion goes to the next model of the ladder as a fresh job with the same packet, with one correction there too. After the last model, the criterion stays unaccounted: criteria accounting (Plan 21, D9) lists it, and the ledger keeps it as an obligation with a gap, and the plan says how many criteria no model answered. A job that returns no answer in the schema (the harness reached its turn limit, or its output is not one object) counts as a failed answer, with the reason as its problem. A provider error (a usage limit, a missing binary, a timeout, a refusal of the schema) ends the run, as it does for the single planner, and says what was spent | A cheap model answers most criteria on the first or the second try, and the few that it cannot answer cost a bigger model one job each, and not a whole plan |
| D8 | The ladder is `semar plan --pipeline criteria --ladder claude:haiku,claude:sonnet,claude:opus`: each step is a provider ID of the person's providers file and a model, from the cheapest up. `plan.ladder` in the person's own `providers.yaml` is the same list for every plan. A repository's `semar.yaml` cannot set it, because it decides which provider receives the code, like `plan.withSetup`. Without a ladder, the criteria pipeline runs on the provider and the model that the single pipeline would use, with `--provider` and `--model`. `--ladder` with `--provider` or `--model` is an error, and so is `--ladder` with `--pipeline single`. A provider is opened once however many steps name it, and its binary is checked before the first job. The reasoning level of a step is the provider's, or `--reasoning` | The strong model is the exception, so it is the last step and not the first. The ladder is also how a person says which providers may see the code |
| D9 | Code assembles the draft. The scenarios come in the order of the criteria, and the kind of each ticket comes from code: `behaviour` when a criterion of it gave a scenario, a manual check, or a `notDrafted` entry, and else `none` with the reason. The sentence of a ticket's behaviour is the title of its ticket file. A title that two criteria share gets ` (criterion <n>)` on the later one. The scenarios over `maxScenarios` become `notDrafted` entries that say so, and stay accounted for. The draft is checked as a whole by the same `Validate`, and the trial runs on it as before: a trial problem goes to the criterion that owns the scenario, in one correction at the model that answered it, and the correction counts only when its expectations are the same, because the trial says what a request does and never what to expect. A behaviour ticket may be covered by manual checks alone | Everything downstream of the draft is unchanged: the writer, the obligations, the ledger, `semar confirm`, and the dashboard |
| D10 | The accepted answers are written to `answers.json` in the plan directory, each with the ticket, the cite, the model, the output, and the hash of its packet. The hash covers the ticket, the text of the criterion, the operations, the diff, the fixtures, the accounts, and the version of the prompt. It does not cover the cite, because a line can move, or the existing scenarios, because a plan adds them. The next plan reads the `answers.json` of the 20 newest plans and reuses an answer whose packet hash is the same, with no job, after the checks run again. An answer that no longer passes, because its title now repeats a scenario that exists, goes through a correction like any other | A plan of a release that changed one criterion should cost one job and not sixteen. An answer is never trusted: the checks are the same |
| D11 | The `model use:` line sums every job and says how the criteria were answered: `model use: 16 jobs (14 haiku, 2 sonnet), 3 corrections, 92k input, 21k output, $0.09`. A job is a criterion, counted under the model that gave its accepted answer. A correction is a call that repaired an answer. The cached part of the input follows the input when the provider reports it, and `, 4 reused` and `, 1 unanswered` follow the cost when they are not zero. The usage log gets one record for each model that was called, so the dashboard shows what each provider and model used. plan.md lists the models with their calls and tokens, a table of the criteria with the model that answered each and its corrections, and the problems that went back to a model | A person can lower what they can see, and a plan that a bigger model had to finish says so |
| D12 | The default stays `single`, and the person asks for the criteria pipeline with `--pipeline criteria`. The evaluation in "Measured" shows that on one release the criteria pipeline with a small model is as good as the single one on every score and costs a twentieth as much. The recommendation under it says what to do with the default: not change it on one release that does not score the quality of a scenario | The default of a command that people have, and that costs them money, changes when a measurement of more than one service says it is better. The decision is the owner's, and it is one line of code |
| D13 | When the API document gives an operation no operationId, code makes a stable name from the method and the path: `post_v1_orders_orderId_refunds`. A declared operationId that is a plain name is used as it is. A name that two operations would share gets `_2`, in the order of the operations. The key is in the packet, the schema, the prompt, and the stored answer | A model that has to choose from a list needs a name for each entry, and the name must be the same in every run, or the hash of a packet would change |
| D14 | An acceptance criterion may be a numbered line, as before, or a group of Given, When, and Then lines under the heading "Acceptance criteria": a line that starts with `Given`, as a bullet or as plain text, and the `When`, `Then`, `And`, and `But` lines after it, until a blank line, a heading, or the next `Given`. The group is one criterion, its number is its place among the criteria of the heading, and its cite is its first line. plan.md tells the writer of a ticket whose criteria are all prose that Given, When, and Then lines are easier for a small model, and the prompt of the single planner accounts for both forms (prompt version 9) | A criterion in the form of a test is already half of the answer, and a small model follows it better than a sentence that mixes the setup, the request, and the result |
| D15 | The OpenAPI reader reads, besides the routes and statuses, the path, query, and header parameters of an operation (with those of the path item), the properties of the JSON request body (OpenAPI 3 `requestBody`, and a Swagger 2 `body` parameter), and the JSON paths of the response bodies, at most five levels deep and 80 fields. It follows `$ref` inside the document, with a bound on hops and work, and a schema that refers to itself stops at the second visit. A document that the second read cannot handle keeps its routes and statuses and has no details | A packet needs the fields that a request may hold, and the check needs them too |

## Contract

### The packet

```text
Packet
  Ticket, Number, Cite        the key, the number and the first line of the criterion
  Criterion                   the text, at most 1,200 characters
  Operations[]                key, method, route, summary, source, params, body, statuses, responses
  Diff, DiffOmitted           the diff of the ticket's files, and the files left out
  Fixtures[], Accounts[]      as the planner prompt lists them
  Account                     the account of a step that names none
  Existing[]                  "<id>: <title>" of the scenarios that exist (not in the hash)
  Version                     the version of the criterion prompt (in the hash)
```

### The answer

```json
{"answer": {"kind": "scenario", "title": "A refund above the order total is refused",
  "intent": "Before: ... Now: ...",
  "given": [{"fixture": "order.paid", "as": "order", "with": [{"name": "customer", "value": "c-1"}]}],
  "steps": [{"id": "refund-too-much", "setup": false, "as": "default", "action": "Refund more than the total",
    "operation": "post_v1_orders_orderId_refunds",
    "path": [{"name": "orderId", "value": "{{order.id}}"}], "query": [],
    "body": [{"field": "amount", "value": 150000}],
    "captures": [],
    "expect": [{"subject": "status", "name": "", "operator": "equals", "value": 422},
               {"subject": "jsonpath", "name": "$.error.code", "operator": "equals", "value": "REFUND_EXCEEDS_TOTAL"}]}]}}
```

A manual check is `{"kind": "manualCheck", "title", "manualSteps": [...], "expected"}`, and a gap is `{"kind": "notDrafted", "what", "needs"}`.

### The commands

| Command | Meaning |
| --- | --- |
| `semar plan --diff <range>` | The single pipeline, as before |
| `semar plan --diff <range> --pipeline criteria` | The criteria pipeline on the provider and the model of the plan |
| `semar plan --diff <range> --pipeline criteria --ladder claude:haiku,claude:sonnet,claude:opus` | The criteria pipeline, from the cheapest model up |

`plan.ladder` in the person's `providers.yaml` is a list of the same `<provider id>:<model>` steps. The `--pipeline` flag is not read from a file.

## Not built

* A body field whose value is a nested object that the planner builds itself. A field of type `object` or `array` takes the text of its JSON, and the check parses it.
* A packet for a ticket that has no acceptance criteria. The criteria pipeline plans nothing for it, and the plan says to use `--pipeline single`.
* Choosing the ladder by measurement. A person writes it.
* `fixturesNeeded` proposals from a job. A criterion that needs a fixture that does not exist is `notDrafted` with `needs: fixture <id>`.
* A first job at a higher model for a criterion that is known to be hard. Every criterion starts at the first step.

## Measured

**What was planned.** The same release of a small mock service as in Plan 23, planned from a clone with its earlier plans removed, with `--no-trial` so that no environment was needed: two tickets with 16 acceptance criteria (11 that an API call can show, and 5 on a web screen, an Android screen, or across both), an API document of 15 operations with no operationId, three accounts, and two fixtures. The answer key lives outside Semar, in the repository of the mock service, so that no file of Semar names the release. It lists the 16 criteria, what the ticket says for the criterion that a move to a list of another board is refused (status 422 and a named error code), and the API document. Its scorer reads the draft that a plan wrote and counts: the criteria that are accounted for (Plan 21, D9); whether one scenario has an expectation of the source ticket for the status 422 and for the error code, with the cite of that criterion, which is the ticket's own requirement and not what the code does; the requests whose route, query parameter, or body field the API document does not declare; the scenarios; and the tokens and the cost of the `model use:` line.

```sh
rm -rf /tmp/eval-plan && git clone -q <the mock repository> /tmp/eval-plan && cd /tmp/eval-plan
git checkout -q release/2026-11-w3 && git branch -q base-main 1eb6642 && git branch -q rel f699f55
git rm -rq .semar/scenarios .semar/obligations .semar/plans && git commit -q -m "remove the earlier plans"
export SEMAR_HOME=$(mktemp -d) && cp ~/.config/semar/providers.yaml $SEMAR_HOME/   # never the real home
semar plan --diff base-main..rel --no-trial --no-fetch <flags below>
(cd <the mock repository>/eval && go run . -repo /tmp/eval-plan -stdout <the standard output of the plan>)
```

The clone was reset between runs. The flags: `--provider claude --model opus` for the baseline, which is the single pipeline; and `--pipeline criteria --ladder claude:haiku`, `claude:sonnet`, `codex:gpt-6-luna`, and `claude:haiku,claude:sonnet,claude:opus` for the others. The reasoning level of each provider is the one in the person's file: `medium` for Claude Code and `high` for Codex. The criteria runs used the build of the commit "a step that expects a refusal may break a validation rule". The baseline used the build of the commit "the single planner accounts for Given/When/Then criteria", two commits earlier, which plans with the single pipeline exactly as the later one does.

**What the numbers say.**

* The answer to the question of the plan is yes on this release: haiku, a small model, accounted for all 16 criteria, gave the status and the error code that the ticket requires, and invented no route or field, as the baseline did, for $0.08 to $0.11 against $1.62 and in 58 to 77 seconds against 287. The jobs of the three Claude and Codex configurations had no tool, so the 16 jobs cost 510k to 790k input tokens, which is more than the 372k of the baseline, at the price of a small model, and run four at a time.
* Sonnet in this pipeline costs the same as Opus in the single one ($1.66 and $1.62). The cost is the input: 16 jobs of two turns each send about 18,000 tokens of prompt and schema, and the price of a Sonnet input token is what it is. The pipeline saves money only through a small model, so the ladder starts there. Where the answer schema is large, the cost of each job is too: 34 KiB of the input of every job is the schema, and it lists every operation. A packet that listed fewer operations would be cheaper, and that is not built.
* Codex with gpt-6-luna needed two fixes before it gave these numbers. With the schema enforced by Codex, as the single pipeline passes it, luna answered `notDrafted` to all 16 criteria: 0 scenarios, and a reason for each, such as that the operations could not create a card although one was listed. The same prompt with the schema as text gave a scenario at once, and so did a run of 10 criteria by hand, in which 4 of 10 answers ended with one closing brace too many. `Job.SchemaInPrompt` (D3) and the tolerance of the Codex driver for a brace too many are the two fixes. The luna run before the second fix had 15 of 16 criteria and 6 corrections.
* The first version of the schema typed each body value. All four configurations then answered the criterion that a position must be a whole number with `notDrafted`, because a model could not send a string for a number. After the change of decision D6 all four wrote a scenario for it, as the baseline had.
* The number of corrections varies from run to run: the haiku runs had 9, 1, 1, and 6, and the ladder runs 3, 2, and 4. A correction costs one job. The criterion that sets a due date to `null` caused corrections in several runs, because a check cannot hold `null` (D6) and a model writes `equals null` first. One earlier ladder run, with the build of the baseline, did escalate: 15 criteria were answered by haiku and one by sonnet.

**What the measurement does not show.** It is one release of one small service, with one run of each configuration and a second run only of the ladder. It scores whether every criterion is accounted for, whether one criterion that the ticket and the code disagree on is expected as the ticket says, and whether a request invents a route or a field. It does not score whether each scenario expects the right thing, whether its steps would pass against the service, or how it compares with the baseline on a service with no API document or no ticket file: the criteria pipeline plans from both and nothing else. The 11 scenarios were not run against the service.

### Recommendation

* **Use the criteria pipeline with the ladder `claude:haiku,claude:sonnet,claude:opus` for a repository that has ticket files with acceptance criteria and an API document.** On the one release measured it is as good as the baseline on every score, and it costs 5% of the baseline and runs in about a fifth of the time. For a person with a subscription of Codex and not of Claude, `codex:gpt-6-luna` alone gave the same scores, and its cost is not reported.
* **Keep `single` as the default for now, and keep it for a change with no ticket file or no API document.** The evidence is one release and does not score the quality of a scenario. The default should change when a second release of another service, with a score for the expectations, shows the same. The change is one line: the default of `--pipeline` in `internal/cli/plan.go`, and a fallback to `single` for a change whose tickets have no criteria or whose documents have no API.
* **Write the criteria as Given, When, and Then lines.** Plan 25 does not measure it against prose, so it is a recommendation of the design (D14) and not of the numbers.
