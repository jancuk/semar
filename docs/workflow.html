Semar test workflow

One ticket, from "deployed on UAT" to "ready for sign-off". The agent tests like a QA engineer. Code checks the result without the agent. Planned design, not built. Draft of 14 November 2026.

Code, no model Agent: planner or tester Fast decision model People Stops here
  1. 1

    Intake Code

    Link each ticket to its merge requests, commits, and changed pieces. Compare with everything that changed on UAT.

    Out: the change set of each ticket, and the build view.

    A change with no ticket, or a ticket with no declared change, stops here.
  2. 2

    Risk and depth Code Screener

    Set a risk level from the paths, the kinds of change, and overlaps. The level sets the number of scenarios, the explore time, and the security level.

    Out: low, standard, or high. The planner can raise it and cannot lower it.

  3. 3

    Plan Planner Code validates

    Read the ticket, the deployed code, the feature map, and earlier testing. Design functional scenarios, access checks, and the security plan with the feature's "must never" rules.

    Out: the test plan, with coverage of the ticket's criteria and of the changed code. An optional second reader from another vendor proposes missing cases.

  4. 4

    Confirm intent Reviewer, not the author

    Answer yes or no questions about expected results that came only from the code, and about proposed rules.

    Nothing waits for the answers. An open question keeps a scenario inconclusive until it is answered.
  5. 5

    Entry check Code

    The change is in the running build on every replica and was not reverted. The accounts are signed in. A few stored scenarios replay as a health check.

    UAT unhealthy, not deployed, or sign-in expired: blocked, and no model is called.
  6. 6

    Test session Tester Pilot

    The agent works as a QA engineer through Semar's tools. Every action is recorded in the activity log.

    ScenariosEach planned scenario, by hand, on the API, the web, and Android.
    ExploreA time-boxed session around the change.
    SecurityCode sends variations of recorded requests. The tester probes business rules.

    Out: recorded actions, a script per scenario, findings, and QA notes.

  7. 7

    Independent check Code

    Replay each script with no model. Read logs and traces in Grafana. Read the data stores, read-only. Compute each outcome. Confirm a security finding only when the recorded actions meet its condition.

    Out: passed, failed, blocked, inconclusive, not run, or stale, with every reason.

  8. 8

    Triage Screener Developer or lead

    A likely cause for each failure, duplicate findings merged, and a defect draft with steps to reproduce. A person decides each suspected finding.

  9. 9

    Report and readiness Code

    Publish the report, the activity log, the list of data touched on UAT, and one comment on the Jira ticket. Compute the readiness line from the exit criteria.

    Out: "ready for sign-off" or "not ready", with every open item.

  10. 10

    Fix and re-test Developer Code

    The developer fixes and deploys. The stored scripts replay on the new build with no model.

    Back to step 5. The agent is called only when a script no longer fits.
  11. 11

    Release Code Release owner

    A regression run replays the suite. A person signs off. The sign-off stops applying when UAT changes. The roll-up shows every ticket of the release.

  12. 12

    Learn Code Approves

    Scenarios and fixed security findings join the regression suite. Confirmed "must never" rules stay with their feature. Notes and map changes need a person's approval.

Rules that hold in every step

The agent decides what to try. Code computes every outcome.
A fast model gives hints and rankings. It never sets an outcome.
Changes to UAT go through the application, as a test account. Data stores are read-only.
The agent never sees a password, a token, or an OTP.
Every action is in the activity log, written by the recorder.
The report says what was tested and what was not. It never says "secure".
