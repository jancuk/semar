After you deploy to UAT

One developer, one ticket, from "the build is on UAT" to "ready for sign-off". This page shows what must be ready, the command you type, what runs at each step, and how you check the result. Planned design, not built. Draft of 14 November 2026.

1. What must be ready

You set this up once per repository. semar doctor checks every item and says which surfaces the setup is ready for.

On your machine Always

  • The Semar binaryStarts its own background daemon and its MCP server.
  • An agent harness, signed inClaude Code or Codex CLI. One is enough.
  • Configuration and feature map.semar/semar.yaml and .semar/map.yaml, in the repository.
  • Read access to the git repositoriesEvery repository a ticket can touch.

Models 2 needed, 3 optional

  • PlannerAn agent on a strong model: Claude Code or Codex CLI. Needed.
  • TesterAn agent: the same, or DeepSeek through Claude Code. Needed.
  • Second readerAn agent from another vendor. Optional.
  • Pilot and screenerTypeSafe's fast model, with a TypeSafe key. Optional. Semar is slower without them.

Connections Own adapter or MCP server

  • JiraRead tickets, post one result comment. A token, or an Atlassian MCP server. Needed.
  • GrafanaRead logs and traces. A read-only token, or a Grafana MCP server. Recommended.
  • Data storesRead-only accounts for PostgreSQL, MySQL, or Elasticsearch. Optional.
  • TestRail, documents, other MCP serversEarlier testing and team knowledge. Optional. Every MCP tool is denied until you list it.

UAT Always

  • Hosts and a build probe per serviceSo Semar can tell which build is running.
  • What tests may change, and a deny listFor example: never a real payment, never a real SMS.
  • Test accounts and the OTP sourceA second account and a lower role make the access checks possible.
  • Per surfaceWeb: Chrome and one semar login. Android: an emulator and the UAT build of the app.

2. Your path, step by step

Blue steps are yours. Everything else runs without you.

You or another person Code, no model Agent Fast decision model Connection it needs
  1. A

    You merge and deploy to UAT You

    As you do today. The merge request names its ticket, for example SHOP-482.

  2. B

    You type one command You

    $ semar verify --ticket SHOP-482
    Or semar verify --new to let Semar find every ticket with new commits on UAT. Or ask your own agent, with the Semar plugin. Or type nothing: in pipeline mode the job starts when the deploy finishes.
  3. 1

    Intake Code

    Finds the ticket, links it to its merge requests and commits, and compares with everything else that changed on UAT.

    JiraGit repositories
    No ticket, or no code change that anyone declared: stops here.
  4. 2

    Risk and depth Code

    Sets low, standard, or high from what changed. A payment or sign-in change gets more scenarios and every security probe.

    Risk paths in the configurationScreener, optional
  5. 3

    Plan Planner

    Reads the ticket, the deployed code, and what was tested before. Writes the scenarios, the access checks, and the security plan. Code then checks every cited line, path, and ticket sentence.

    Claude Code or Codex CLIFeature mapTestRail, documents, MCP knowledge toolsSecond reader, optional
  6. 4

    Entry check Code

    The merge is in the running build and was not reverted. The accounts are signed in. A few stored scenarios replay to show that UAT is healthy.

    Build probesTest accounts, OTP source
    Not deployed, UAT unhealthy, or sign-in expired: blocked, and no model has been called.
  7. 5

    Test session Tester Pilot

    The agent tests like a QA engineer: it works through each scenario, explores around the change, and tests security. Semar types every secret itself and records every action.

    Claude Code, Codex CLI, or DeepSeekTypeSafe Jev, for pages and screensSemar's own MCP serverUAT hostsChrome profile, emulator
  8. 6

    Independent check Code

    Replays each script with no AI. Reads logs and traces for this run. Reads the data stores where a check needs them. Computes each result.

    GrafanaRead-only data store accounts
  9. 7

    Triage and report Code Screener

    A likely cause and a defect draft for each failure. Then the report, the activity log, the data left on UAT, and one readiness line.

    Evidence storeJira comment
    Result     SHOP-482  3 passed, 1 failed, 2 inconclusive (waiting for an answer)
                     1 confirmed security finding, 2 suspected
Data       3 orders created, 2 cleaned up, 1 still on UAT (order 81240)
Ready      SHOP-482  not ready for sign-off: 1 failed, 1 finding, 2 questions
Report     .semar/runs/r-20261114-0042/report.md
  10. C

    A reviewer answers the questions Not the author

    Only expected results that came from the code alone are asked, as yes or no. Semar then recomputes the result from the stored evidence. It does not test again.

    SHOP-482, scenario 2
A refund equal to the order total is still accepted. Yes or no?
Source: refund.go:42. The ticket does not say.
  11. D

    You fix what failed, and Semar tests again You Code

    Each failure has a defect draft with the steps that ran. After your fix is on UAT, the same command replays the stored scripts with no AI.

    $ semar defect SHOP-482-01      # steps, expected, actual, evidence
$ semar run --scenario SHOP-482-01   # reproduce it, no AI
$ semar verify --ticket SHOP-482     # after the fix is deployed
  12. E

    The release owner signs off Release owner

    When every ticket reads "ready for sign-off". The sign-off names its builds and stops applying when UAT changes.

    SHOP-482  ready for sign-off   6 passed, security testing: no confirmed finding

3. How you gain confidence in the result

A green line from an AI tool deserves doubt. These are the checks you can make yourself.

One result

  • The sourceEach expected result names where it came from: the ticket, a test case, a person, or the code.
  • The evidenceThe recorded request and response, or the screenshot. The agent's words are never evidence.
  • The judgeCode computes the result. The agent cannot pass its own work.
  • The replayThe script runs again with no AI and must give the same result.

One ticket

  • Two coverage tablesEach criterion of the ticket and each changed piece of code, with its scenarios or "none".
  • The second-look listUncovered changes, overlaps, and changes the ticket does not mention.
  • The activity logEvery action, and every record created, changed, or deleted on UAT.
  • The readiness lineWhat is open, and what was not tested.

The tool itself

  • Shadow firstRun beside your current testing and compare, before anyone relies on it.
  • Mark a wrong resultFalse passes and false failures are counted per feature.
  • A random sampleEach release, code picks a few passes for a person to open.
  • Seeded defectsEach Semar release is run against an application with known defects.
